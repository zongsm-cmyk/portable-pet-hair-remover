# VerveLiving order gateway

Cloudflare Worker + D1 implementation, deployed on `shop.askouresystems.com/api/*` with checkout disabled and Sandbox mode. Tests use local SQLite and mocked PayPal responses; they do not prove real Sandbox, live payments or CJ import acceptance. See production receipts for actual HTTP and D1 evidence.

## API contract

- `GET /api/health`: operational state only, no credentials.
- `POST /api/orders/create`: `{items:[{id,quantity}],country:"US"|"GB"}`. Returns `order_id`, `paypal_order_id`, `approval_url`, and server-calculated USD total. Redirect to the PayPal approval URL. The storefront return page calls capture using the `token` query value; this is the PayPal order ID, not proof of payment.
- `POST /api/orders/capture`: `{paypal_order_id}`. Optional caller cart values are ignored. Loads the durable original quote, retrieves the PayPal order, validates merchant/reference/USD/amount/country before capture, captures approved orders with a stable request ID, retrieves and verifies the completed capture, and stores the receipt atomically. A replay returns the existing receipt. If the provider succeeded but a network or D1 error occurred, retry this same PayPal order ID; the handler retrieves completed captures instead of creating another payment. Do not create a replacement payment to recover an uncertain capture.
- `POST /api/orders/track`: `{order_id,email}`. Returns only order ID, fulfillment status and tracking fields. A GET form is also supported to match the requested API, but POST avoids placing email addresses in URL logs. No customer identity or address is returned. Twenty lookup attempts per source IP per ten minutes, hashed D1 limit keys, daily expiry cleanup.
- `GET /api/orders/export-cj-csv`: `Authorization: Bearer <ADMIN_TOKEN>`. Returns at most 500 paid, unfulfilled orders, one row per line item. Export does not mark an order fulfilled; do not re-import a prior batch. Authenticated exports contain customer data and must remain private.
- `POST /api/orders/fulfillment`: same admin authorization; `{order_id,fulfillment_status:"shipped"|"delivered",tracking_number,tracking_carrier}`. Updates only a paid order, rejects malformed tracking details and delivered-to-shipped regressions. This records tracking locally; the response explicitly says `external_notifications_sent:false`.

The gateway does **not** yet send shipment emails, submit CJ orders, post PayPal tracking, or reconcile refunds/disputes by webhook. These are separate integration work. Order records remain `unfulfilled` until an authenticated fulfillment update records a real shipment. Do not claim external tracking automation is live.

New checkouts are limited to ten requests per source IP per ten minutes. Before charging an approved PayPal order, the gateway checks its exact provider order ID and requalifies the original cart against the current authoritative catalog, rejecting withdrawn products, stale supplier evidence, changed supplier SKU/variant, and changed prices/shipping. Completed captures can still be recovered into D1 even if a product is subsequently withdrawn; recovery never charges the buyer again.

## Authoritative catalog

`catalog.generated.json` is generated by `scripts/build_store.py` from `data/catalog.json`, with shape `{products:[...]}`. Never accept browser price or supplier fields. `shipping_us_usd`/`shipping_uk_usd` are supplier costs, not charges added to the shopper total. Customer charges use optional `customer_shipping_us_usd`/`customer_shipping_uk_usd` fields, defaulting to zero; for verified offers the retail price must cover included delivery costs. Each unit's shipping charge is counted per unit, not once per basket.

Eligibility requires `verified_for_checkout === true`, known CJ SKU and variant, an HTTPS CJ product URL, warehouse, supplier cost, destination shipping cost, `stock_status: "in_stock"`, `supplier_verified_at` no older than seven days, ETA in `8-14 business days` style with upper bound <=14, and `specs.weight_g` >0 and <500, `specs.contains_lithium: false`, `specs.contains_liquid: false`, `specs.medical: false`. These values must come from actual supplier evidence, not guessed data. Future catalog qualification should review profitability and source evidence before setting the flag. Unverified drafts stay false.

## Deployment prerequisites

1. Use the authorized Cloudflare account with no plan upgrade or paid resource attachment. A real D1 database and narrowly scoped route are configured in `wrangler.toml`; identifiers are configuration metadata, not authentication secrets.
2. Apply `migrations/0001_orders.sql` locally, then to the real D1 database only when ready. Node tests apply the same SQL to an in-memory SQLite database.
3. Bind route `shop.askouresystems.com/api/*` within the owned Cloudflare zone (or change the storefront API base if using a separately configured hostname). Static GitHub Pages cannot execute these endpoints.
4. Set secrets through `wrangler secret put`: `PAYPAL_CLIENT_ID`, `PAYPAL_CLIENT_SECRET`, `PAYPAL_MERCHANT_ID`, `ADMIN_TOKEN`. The admin token must be at least 24 characters. Never put keys, PII or database exports in Git or static output.
5. Keep `PAYPAL_ENV="sandbox"`. Explicitly setting `CHECKOUT_ENABLED="true"` is only appropriate once supplier evidence and the Sandbox flow are ready. Both global and per-product gates apply. An approved checkout intent expires after 30 minutes; completed payments can still be recovered.
6. Complete a real **Sandbox** create/approve/capture/replay/export exercise with a Sandbox merchant and buyer. Do not describe the mocked test as this exercise. Verify CORS/origin, route, support mailbox, actual CSV import, and D1 access restrictions. Then separately establish merchant limitations/holds and fulfillment float before live enablement. No funds were transferred by this implementation.

Free plans have quotas; this configuration is not a guarantee of unlimited operation or zero payment/fulfillment costs.

## CJ CSV template gate

The exact current CJ import template has **not** been downloaded from the connected CJ account. Export therefore fails closed with `cj_template_unverified` until the current account-specific template is obtained and mapped. Do not label a guessed header layout as CJ compatible. Set secret `CJ_TEMPLATE_JSON` after verifying the official template, preserving header text and order:

```json
{"verified_at":"<actual verification timestamp>","source_url":"<actual official template source>","columns":[{"header":"<exact CJ header>","field":"order_id","required":true}]}
```

The example is a configuration shape, **not a CJ template**. Available fields: `order_id`, `customer_name`, `email`, `address_line_1`, `address_line_2`, `city`, `state`, `postcode`, `country`, `cj_sku`, `cj_variant_id`, `quantity`, `total_paid_usd`, `phone`. Phone is currently empty; if the actual template requires it, mark `required:true`, and export will refuse incomplete rows until phone collection is integrated. CSV quoting protects comma/newline values and prefixes formula-like cells to prevent spreadsheet execution; validate how the official importer handles this before enabling imports. Store no customer data in the public feed or catalog.
