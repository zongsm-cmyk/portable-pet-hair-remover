# Sandbox acceptance, currently NOT RUN

Use Node 24 and the existing Worker. No live payment, purchase, paid service or plan change is part of this runbook. Do not place credentials or buyer details in Git, static files, screenshots or receipts.

1. Run `node --test tests/*.test.mjs workers/order-gateway/test/*.test.mjs` and the Python suite. These are mocks, not provider acceptance.
2. Obtain real supplier evidence using `data/merchant-evidence.template.json`. The template never sets checkout eligibility. Independently review exact VID, stock timestamp, country/quantity shipping quote, duties, returns, QC and rights. Do not replace missing evidence with assumed prices or profitability. Importing research media does not qualify products.
3. For an isolated local Sandbox exercise only, use a private, ignored `.dev.vars` in `workers/order-gateway` with named variables `PAYPAL_ENV=sandbox`, `PAYPAL_CLIENT_ID`, `PAYPAL_CLIENT_SECRET`, `PAYPAL_MERCHANT_ID`, `ADMIN_TOKEN`, `STOREFRONT_ORIGIN`, `CHECKOUT_ENABLED`. `ADMIN_TOKEN` requires at least 24 characters. `DB` is the existing local D1 binding. Use a Sandbox business app/merchant and a separate Sandbox buyer. Do not use live credentials. Keep repository `wrangler.toml` and public settings disabled. A test-only catalog fixture must stay outside published files and be labelled synthetic, with no claim of real stock.
4. With the existing Wrangler installation, apply the existing migration locally using `wrangler d1 migrations apply verveliving-orders --local`, then `wrangler dev --local`. Configure only the private local exercise environment for enabled Sandbox access. Do not deploy an enabled gateway or overwrite the production catalog to run a test. If Wrangler/credentials are unavailable, record NOT RUN and stop the provider test.
5. Submit IDs, integer quantities and `US` or `GB` to `POST /api/orders/create` from the configured origin. Never send browser prices as authority. Save the returned internal and PayPal order IDs privately. Approve once using the Sandbox buyer at exactly `https://www.sandbox.paypal.com`. Confirm seller, destination, currency and amount before approval. A redirect alone proves no payment.
6. Call `POST /api/orders/capture` with the same `paypal_order_id`. Require `payment_status=COMPLETED`, a valid internal order ID, a single completed provider capture with the intended merchant/currency/amount/country, and exactly one persisted D1 order. Read the provider record and D1 independently. Replay the same capture request and reload the return page: the original receipt must return, with the same capture ID and no second provider capture or order.
7. Test cancel, expired/revoked qualification and price changes. The gateway must refuse an unqualified new capture. Existing completed payments must be recoverable without charging again. For a timeout, unknown outcome or failed D1 write, retrieve the ORIGINAL PayPal order; do not create another payment. Capture uses the stable `cap-<internal order UUID without hyphens>` request ID and retrieves completed provider state before reconciliation. D1 unique order/payment/capture constraints are a second guard. These controls rely on provider semantics; mocked replay is not proof of a real concurrent provider run.
8. Order creation is a new intent per request, without a client retry key. Do not replay an uncertain create request. The cart disables checkout and edits after submission and does not automatically retry. Resolve the original intent/provider order before another attempt.
9. Check private order lookup with correct and wrong email, rate limiting, authenticated export only after real `CJ_TEMPLATE_JSON` account-template verification, and manual tracking readback. Never submit a paid CJ purchase during acceptance. Email notification, PayPal tracking submission and refund/dispute webhooks are not operational acceptance claims.
10. Record timestamps, redacted IDs, actual server/provider state, replay results and the exact tested commit outside the public repository. Keep credentials and customer data out of receipts. Restore local checkout disabled. Live enablement still requires separate real merchant proof, supplier qualification, account-specific CJ export validation, inbound support delivery and operational returns evidence. No real Sandbox transaction has been completed by the current code work.
